# ADR 0003 — Rust core + Swift shell (amends 0001)

- **Status:** accepted
- **Date:** 2026-06-06
- **Amends:** [0001](0001-tech-stack-and-integration.md) (tech stack & integration);
  supersedes [0002](0002-juce-fetchcontent-headless.md) (JUCE FetchContent), which is now moot.
- **Related:** `doc/SRD_core_engine_v0.1.md` (the core-engine SRD this enables),
  `doc/SRD_v1.1.md` (system SRD).

## Context
ADR 0001 chose a **C++/JUCE** headless core with a **Python lab** integrated via
**pybind11** (scikit-build-core, JUCE via FetchContent). We built that through M1 and
M2 (a working C++ engine: loop-doc render, modulators, voice engine, DSP). Two things
then changed the calculus:

1. **The integration was painful and the C++ wasn't carrying us.** A code review of M2
   found the engine was procedural rather than object-oriented (a ~500-line render
   function, stringly-typed DSP-state maps, no voice/synth object model), and several
   correctness/portability gaps (priority-aware voice stealing unimplemented;
   `std::hash` used for determinism keys — not portable across platforms; stair-stepped
   modulation → zipper-noise risk; `swing`/`timing_jitter`/`humanize` parsed but never
   applied). Separately, the pybind11 + scikit-build-core + FetchContent build (and the
   "must rebuild after every C++ edit or silently serve a stale binary" footgun) was a
   persistent source of friction.

2. **The product shape sharpened.** The core engine is now explicitly intended to be
   the **shipped iOS MVP core**, and the requirements hardened to the **full online
   loop**: live audio streaming + antithetic ±δ dithering + **on-device CLAP scoring**
   + **online RLS learning** + complete sample export, all in one native app
   (macOS-first, port to iOS). This makes everything native and real-time; Python
   retreats to an **offline** role (training, sweep rig, `fake_clap` harness) consuming
   an exported corpus over a file boundary — so the hot in-process Python binding
   disappears regardless of language.

Key realizations that unblocked reconsidering the stack:
- **JUCE usage was thin** (one filter, one reverb, WAV I/O, an oscillator used only in
  a smoke test), and JUCE is **not a hard requirement** — FunDSP/own DSP is acceptable.
- **On-device CLAP is language-neutral.** It runs via **ONNX Runtime** (C++ *and* Rust
  bindings) or **CoreML** (callable from Swift/Obj-C++); text-tower embeddings are
  precomputed offline so only the audio encoder runs on device. So CLAP does not pick
  the language; and in a Swift-shell topology CLAP sits in **Swift+CoreML** (the easiest
  on-device path) and feeds scores to the controller as plain numbers.
- The hard requirements that *do* discriminate — **mandatory determinism** (portable,
  bit-reproducible) and a **real-time audio-thread + worker-thread + lock-free** design
  — favor Rust (no UB, reproducible; the borrow checker prevents exactly the
  audio-thread data races that are worst to debug).

## Decision
Build the core engine + controller as a **Rust, I/O-free core library** (`sme_core`),
driven by a **thin Swift shell** (macOS CLI now; SwiftUI iOS app later):

- **Core (Rust):** synthesis, loop sequencer, modulators, matrix, controller, online
  RLS, observation/capture, sample export. No audio device, no files, no wall-clock,
  **no linked ML model**. Ships as `staticlib`/`cdylib` with a C ABI generated by
  `cbindgen`. Recompiles unchanged for `aarch64-apple-ios`.
- **Shell (Swift):** owns the audio device via **AVAudioEngine** (same API on
  macOS/iOS), runs the worker thread, hosts the **CLAP `Scorer`** (CoreML/ONNX; with
  `fake_clap` and null implementations swappable), writes the corpus, and exposes the
  CLI flags. Holds **all** platform specifics.
- **Python lab:** offline only — consumes the exported corpus (JSONL/Parquet) over a
  file boundary. No pybind11. The existing `lab/` Python tests are kept as the
  language-agnostic behavior spec to port into Rust-core acceptance tests.

The CLAP model is **injected behind a `Scorer` interface**, never linked into the core —
keeping the sample complete-on-emission while the core stays platform-agnostic, and
making `fake_clap` a trivial swap for independent learner validation (system SRD §8.3).

## Consequences
**Positive**
- Determinism and real-time concurrency safety are language-enforced (CE-R7, CE-R3.3).
- `cargo` + `cbindgen` replace CMake/FetchContent/scikit-build-core; `serde` +
  Arrow/Parquet give a clean corpus writer; the in-process Python binding is gone.
- One core library with thin front-ends (CLI now, iOS app later) realizes the
  portable-core requirement (system SRD R11.6) literally.
- CLAP lives in Swift+CoreML (the easiest on-device path); the core never touches a model.

**Negative / costs**
- A **Rust↔Swift C-ABI seam** exists in the product (designed once via `cbindgen`).
- **iOS audio I/O** will likely need a small Swift/AudioUnit glue layer (cpal's iOS
  backend is weaker); on macOS the shell uses AVAudioEngine directly.
- We **rewrite the engine** (the M2 C++ work is preserved in git history at commit
  `6b7699b` for reference; the DSP is small, reverb being the only non-trivial port).
- Swift's audio/CoreML ergonomics are first-class on Apple platforms but tie the
  *shell* to Apple; the **core** stays portable (Android later would need its own shell).

## Alternatives considered
- **C++20 + idiomatic JUCE, single codebase** (no Swift, JUCE owns audio I/O + UI). The
  lower-FFI-boundary path and the conventional audio-app choice, but it keeps us in the
  ergonomics we were unhappy with and imposes real-time C++ discipline; JUCE's value is
  mostly in the app-shell concerns we don't need in the headless core. Rejected given
  JUCE became optional and the determinism/concurrency/maintainability balance.
- **Keep C++ but swap pybind11 for a CLI/process boundary** (less change, kills the
  build pain). Would have worked for the POC, but doesn't address the structural/
  ergonomic dissatisfaction and keeps C++ as the shipped-core language.
- **Everything in one language including CLAP** (e.g. reimplement CLAP via candle/ONNX
  in the core). Out of scope for the POC; CLAP stays an injected, converted graph.

## What this changes in 0001
- Engine core: **C++/JUCE → Rust** (I/O-free, `cbindgen` C ABI).
- Integration: **pybind11 in-process → file/CLI boundary**, Python offline-only.
- Shell/runtime: adds a **Swift shell** (AVAudioEngine + CoreML), macOS-first → iOS.
- Unchanged from 0001/the SRDs: determinism mandate, the loop-doc v0.6 contract,
  feature-vector learning, antithetic ±δ baselines, portable core behind interfaces.
